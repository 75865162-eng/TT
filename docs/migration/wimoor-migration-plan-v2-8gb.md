# 条条 ERP → Wimoor 迁移与瘦身实施方案 v2（8GB 单机版）

> **本文替代 v1**（`/workspace/wimoor-migration-slim-plan.md`）。v1 基于 2GB 内存、迁历史数据、含赛狐；三项前提已变，v2 全部重算。
> 目标系统：**Wimoor（Spring Boot 2 + Vue3）为唯一维护系统**。
> 页面基线：《菜单 href 一二三级对照》（2026-11-24 快照）+ 2026-11-25 引用审计。
> 版本：2026-11-25

---

## 一、三项前提变更 → 对方案的连锁影响

| 前提 | v1 假设 | **v2 现状** | 带来的变化 |
|---|---|---|---|
| 服务器内存 | 2GB（已吃 swap） | **8GB 新机** | **不再需要单体化改造**；原生微服务架构 + 内存调优即可稳定运行。这是本版最大的简化 |
| 历史数据 | 要迁 PostgreSQL→MySQL | **不要，数据从空库重来** | 删除全部 ETL / 数据迁移 / 双库并行期；不再是风险项 |
| 赛狐模块 | 112 文件全迁 | **不要，剔除** | P2 工作量减半（只剩 WMS 增强 61 文件）；工期缩短 |

**连锁结论**：v1 里两个最重、最险的工作——「10 微服务裁成 3 进程的 Java 改造」和「跨库数据迁移」——在 v2 里**都不用做了**。剩下的是"部署调优 + 页面瘦身 + 增量功能移植"，风险与工期显著下降。

> 一句话 v2：在 8GB 新机上用**原生 Wimoor 架构**（仅关 Seata、JVM 小堆调优）跑起来；按审计口径砍掉 389 个无引用页面；把条条 ERP 的独有能力（WMS 增强 / Lili / 选品 / AI 对话，赛狐除外）作为增量模块迁入；最终只维护 Wimoor 一套。

## 二、现况基线（已核实事实）

### 2.1 两套系统

| 维度 | 条条 ERP（当前生产，将下线） | Wimoor（目标，唯一维护） |
|---|---|---|
| 代码库 | `/workspace/woker` | `/workspace/wimoor` |
| 技术栈 | Next.js 15 / TypeScript | Spring Boot 2.6.13 / Java / Vue3 / Element Plus |
| 数据库 | PostgreSQL | MySQL 8（8 个库：admin/amazon/amazon_adv/erp/finance/quartz/quote/datamove） |
| 架构 | 单体 + 6 个 Node worker | 10 个 Spring Boot 服务 + Nacos + Redis + Gateway（**Seata 默认关**） |
| 规模 | 93 `page.tsx`，251 API，51 lib | **734 `.vue`**，~4500 Java 文件，~300 Controller，756 张表 |
| 部署 | aoocy.com 在跑，6 服务 active | 从未部署，仅本地源码 |
| 页面基线 | — | 菜单清单 12 一级 / 39 二级 / 160 三级，引用 126 个组件（100% 存在） |

### 2.2 关键架构事实（来自 P0 调研，决定部署方案）

1. **网关单端口统一分流**：前端所有 `/admin` `/erp` `/amazon` `/finance` 等 API 都走 gateway(8099)，由网关按前缀转发到各服务。→ 不用改前端 API 走向。
2. **Seata 可完全不启**：`wimoor-commom-ext` 里 `seata.enabled=false`，全代码 `@GlobalTransactional` 仅 1 处。→ 省一个 JVM（~400MB）和复杂度。
3. **数据库脚本齐全**：`init-config/mysql/数据库结构/*`（空结构）+ `init-config/mysql/数据/*`（基础数据）；Nacos 配置在 `init-config/nacos/DEFAULT_GROUP/*`。→ 空库起步完全可行，正好匹配"不要历史数据"。
4. **默认管理员**：`t_user.sql` 中 `admin@wimoor.com`（加密密码见文件）。
5. **Spring Boot 2.6.13 + Java**：本地 Java 20 编译时 `java.version=9` 会报错，构建用 `-Djava.version=17` 或 Docker 固定 JDK 17。

### 2.3 页面引用审计结论（2026-11-25，决定瘦身口径）

对 734 个 `.vue` 做全源码引用扫描（1106 个源文件，抽查 10/10 命中）：

| 分类 | 数量 | 处置 |
|---|---:|---|
| 菜单白名单 | 126 | 保留 |
| 🔴 静态路由引用 | 61 | **必须保留**（删了 404，含首页 `dashboard/index`） |
| 🟠 被在用页面 import | 134 | **必须保留**（保留页的子组件，删了编译报错） |
| 🟡 SQL 隐藏菜单配置 | 24 | 待复核（visible=0/不可达，P5 前确认） |
| 🟢 无在用引用 | **389** | **可安全删除** |

→ **v1「删 608」作废**。真实可删 389；保守保留 345（126+219），其中 24 个 SQL 菜单项在 P5 前二次确认后可再清。

> 更正 v1 错误：v1 说 dashboard/customized「100% 全删」——实际 `dashboard/index` 被 `router/index.js` 静态注册，是登录落地页，**不能删**。

## 三、8GB 架构决策（v2 核心）

### 3.1 为什么不再单体化

v1 因 2GB 内存被迫规划"10 微服务 → 3 进程"的 Java 代码级改造，这是整个方案里风险最高、最容易失败的部分。8GB 让这条路**不必要**：原生架构内存调优后即可装进 8GB 且留有余量，改造风险直接归零。

### 3.2 8GB 内存预算（原生架构，JVM 调优后）

| 组件 | 端口 | 堆/缓存配置 | 预估常驻 |
|---|---|---|---:|
| MySQL 8 | 3306 | `innodb_buffer_pool_size=512M` | ~700 MB |
| Redis 7 | 6379 | `maxmemory 128M` | ~60 MB |
| Nacos 2.x 单机 | 8848 | `-Xmx256m` | ~400 MB |
| Gateway | 8099 | `-Xmx256m` | ~300 MB |
| admin | 8100 | `-Xmx384m` | ~400 MB |
| erp | 8101 | `-Xmx512m` | ~550 MB |
| amazon | 8102 | `-Xmx512m` | ~550 MB |
| amazon-adv | 8103 | `-Xmx512m` | ~550 MB |
| finance | 8106 | `-Xmx384m` | ~400 MB |
| data / quote / gen（按需） | 8104/8105/8107 | `-Xmx256m` each | ~900 MB |
| 系统 + page cache | — | — | ~600 MB |
| **全服务合计** | | | **~5.4 GB** |

**8GB 留 ~2.6GB 余量**；P0 最小集（MySQL/Redis/Nacos/Gateway/admin/erp）仅约 2.4GB。Seata 不启（默认关）。

> JVM 统一 `-XX:+UseSerialGC -XX:MaxMetaspaceSize=160m -Xss256k`；前端构建为静态文件由 Nginx 托管，不跑 Node 服务。

### 3.3 "降内存"目标重新定义

v1 目标是"从 1.57GB+swap 降到 1.2GB"（因老机器只有 2GB）。v2 换成 8GB 新机后，目标变为：**Wimoor 全功能在 8GB 上稳定运行、常驻 <6GB、不碰 swap、留 2GB+ 余量**。原生架构调调优后即达标，无需架构牺牲。

## 五、瘦身方案（按审计修正）

### 5.1 页面瘦身

- **保留**：126 菜单组件 + 61 静态路由 + 134 在用依赖 = **321 个必须保留**；另 24 个 SQL 菜单项待复核（全保留则 345）。
- **删除**：**389 个无在用引用页面**（🟢 SAFE）。其中"仅被其他待删页引用"的须与引用方**同批删除**。
- **方法**：以审计的白名单（321 或 345）为准，脚本扫描 `views`，名单外的 `.vue` 先移入归档目录并打 git tag，验证无引用后再彻底删除。
- **菜单同步**：`t_sys_menu` 裁剪到清单内结构；🔴 静态路由与 🟠 子组件不在菜单里，但**代码保留**，不参与菜单裁剪。
- **二次清理**：24 个 🟡 SQL 隐藏菜单项在 P5 前结合 `visible=0` 状态与业务确认，决定是否随最后一批清理。

### 5.2 后端 / 数据瘦身

- 后端：用 Controller→Service→Mapper→表的依赖图分析孤儿代码，只删确认无引用的部分；先归档到 tag，冒烟测试通过后删。
- 数据：**8GB + 不要历史数据**，表结构可整体保留（756 张表不改变内存瓶颈），**不做激进删表**——这是相对 v1 的收敛，避免误删隐含依赖（如 seata/quartz 运行时表）。

## 六、分阶段实施计划（v2，约 6~9 周）

每阶段独立可验收、可回滚；P0 通过前不动生产。

| 阶段 | 目标 | 关键动作 | 验收标准 | 周期 |
|---|---|---|---|---|
| **P0 地基** | Wimoor 在 8GB 单机跑起来 | Docker Compose 编排 MySQL/Redis/Nacos/Gateway/admin/erp；导入空表结构 + db_admin 系统数据；Nacos 配置本地化；JVM 调优；关 Seata | 6 容器 healthy；登录 → 12 一级菜单 → 产品管理可打开；`docker stats` <3GB | 3~5 天 |
| **P1 页面瘦身** | 页面收敛 | 归档 389 个无引用页面 + 菜单裁剪；保留 321/345 | 菜单只剩 12/39/160；清单内页面无 404；🔴🟠 页面仍可访问 | 3~5 天 |
| **P2 WMS 增强迁移** | 条条 WMS 增量能力迁入 | 移植 61 文件（库龄/盘点打印/成本调整/库存风险/货值）到 `wimoor-erp` | 与条条 ERP 逐字段对账一致；真实数据双跑比对 | 1~1.5 周 |
| **P3 AI 能力迁移** | AI 模块迁入 | 移植 Lili/Skill 引擎/选品/AI 对话 + 卖家精灵/西柚只读源（含积分计量） | skill_list/get/run 可用；积分计量按影子模式生效 | 2~3 周 |
| **P4 报表补齐** | 细粒度报表补齐 | 对照补 Wimoor 缺失指标 | 清单内报表均可查真实数据 | 1~2 周 |
| **P5 切换与下线** | 切流量到 Wimoor | 复核 24 个 🟡 菜单项并按需清理；DNS/反代切换；观察；条条 ERP 转只读归档 | 常驻 <6GB、无 swap、全功能可用、稳定 7 天 | 1 周 |

**对比 v1**：省掉单体化 Java 改造（原 P0 高风险项）与数据迁移（原风险项）；P2 因剔除赛狐减半。总工期 8~12 周 → **6~9 周**。

| 风险 | 影响 | 对策 |

## 八、需要你拍板（影响计划启动）

1. **卖家精灵/西柚是否保留**：v2 默认保留在 P3（因你之前要求积分计量）。若也不要，P3 再减，请明确。
2. **8GB 机器部署位置**：新 8GB 机是替换现有 2GB 服务器，还是另开一台与生产共存？P0 建议在与生产隔离的环境做，P5 再切换。
3. **登录验证码**：P0 是否允许临时关闭、用固定测试账号登录？
4. **切换方式**：一次性切换，还是按板块渐进？渐进更安全但双系统维护期长。
